# mattermost-plugin-recurring 要件

## 背景・目的

Mattermost には繰り返しリマインダーが存在しない。組み込みのメッセージリマインダー(v7.10〜)は単発のみで
「recurring reminders isn't supported」と明記されている。埋めていたはずの
`scottleedavis/mattermost-plugin-remind` は 2023-11 にアーカイブ済み、
`mattermost-community/mattermost-plugin-todo` は最終リリース 2023-10 で停滞し、
繰り返しリマインダーの要望(issue #61)は 2020 年から6年放置されている。
Marketplace 上の実質的な空席を、繰り返しに特化した小さく保守可能なプラグインで埋める。

**成功条件**: 自サーバー(mm.w4ta.com)で「毎週月曜10時に週次報告を書く」というリマインダーが
自分に届き続け、RHS から一覧・編集・削除・完了できる。その状態で Marketplace へ申請できる品質にある。

## ユーザー

不特定多数に公開する(Mattermost Marketplace 掲載を目指す)。
第一のユーザーは自分自身で、自サーバーで常用しながら育てる(ドッグフーディング)。

## スコープ

### やること(MVP)

- **繰り返しリマインダー**: 「毎朝9時」「毎週月曜10時」「平日18時」「毎月1日」などの周期指定で
  自分宛 DM に通知。プラグインのコア価値。
- **単発リマインダー**: 「30分後」「明日9時」など一回限り。スラッシュコマンドから直接打てる利点。
- **RHS 一覧 UI**: 右サイドバーでリマインダーの一覧・作成・編集・削除。
  Marketplace 申請に必要なスクリーンショットの主題にもなる。
- **一時停止と再開**: リマインダーを消さずに止められる。
  当初は「完了チェック」を予定していたが取りやめた。繰り返しに対する「完了」は
  「今回の分を消した」のか「ルール自体を畳んだ」のかが定義できず、
  ユーザーの解釈と実装が食い違う。To Do プラグインとの機能重複も避けられる。
- **入力方式は自然語 + 構造化 UI の両方**: スラッシュコマンドは日本語・英語の自然語をパースし、
  RHS では曜日・時刻のピッカーで指定する。
- **i18n**: 英語を正、日本語を同梱。

### やらないこと(今回は)

- **チャンネル宛リマインダー**(他人を巻き込む投稿)。権限設計とスパム耐性の検討が必要なため M3 以降。
- **他ユーザーへのリマインダー割り当て**(todo プラグインの Assign 相当)。
- **cron 式の直接入力**。一般ユーザー向けでないため。ただし内部表現は cron 相当の表現力を持たせる。
- **todo プラグインとのデータ連携**。相手が停滞しているため依存しない。
- **独自DBテーブル・マイグレーション**。KV Store のみで完結させる。
- **Calls/通話や外部サービス連携**。

## 技術選定

| 項目 | 選定 | 理由 |
|------|------|------|
| サーバー | Go 1.25 + mattermost/server/public/pluginapi | Mattermost プラグインの標準構成。他に選択肢がない |
| スケジューラ | `pluginapi/cluster.Schedule` による1分ごとの定期スイープ | クラスタセーフ(複数インスタンスでも同時に1つだけ)。KV のリマインダーだけが状態で、ジョブという別状態を持たない |
| 繰り返しの実現 | スイープで `NextRunAt` を過ぎたものを配信し、その場で次回を計算して書き戻す | `JobOnceScheduler` での自己再帰は不可(下記) |
| フロントエンド | React + TypeScript (webapp プラグイン) | Mattermost の webapp プラグインは React 前提。RHS 登録も React コンポーネント |
| データ | プラグイン KV Store のみ | DB マイグレーション不要、Postgres/MySQL 両対応、Marketplace のセキュリティレビューを通しやすい |
| 自然語パース | 自前実装(日英) | 既存 Go ライブラリは英語偏重で日本語の「毎週月曜」を扱えない。依存を増やさない |
| ビルド | Mattermost 公式 plugin starter template の Makefile 系 | Marketplace 申請時の tar.gz 構成・署名フローに乗るため |

## 設計上の決定と失敗の記録

### JobOnceScheduler を繰り返しに使うのは不可能(2026-09-03 に一度実装して撤回)

当初は `cluster.JobOnceScheduler` に「次の1回」を預け、発火コールバックの中で
次回を `ScheduleOnce` し直す設計にしたが、動かないことが判明して作り直した。

- コールバックはそのキーの**クラスタミューテックスを保持したまま**呼ばれる
  (`cluster/job_once.go` の `run()`)。同じキーの `ScheduleOnce` は
  `saveMetadata` で同じ非再入ロックを取りに行き、自分自身を待って恒久デッドロックする。
  再現テストで確認済み。
- `executeJob` は全コールバックを1つのミューテックスで直列化するため、
  1件詰まるとそのインスタンスの全ユーザーの全リマインダーが止まる。
- `saveMetadata` は `Atomic/OldValue:nil` で既存キーを上書きできない。
  `ScheduleOnce` の doc も「reschedule するなら先に cancel しろ」と明記している。
- コールバックから戻った直後に `cancelWhileHoldingMutex` がジョブレコードを削除する。

**教訓**: スケジューラの結線を通す統合テストが無かったため、
中核機能が一度も動かない状態でコミットされていた。文字列操作のユニットテストだけでは
この種の欠陥は検出できない。

## マイルストーン

- **M1(最小の動くもの)** — 2026-09-03 達成: `/recurring 毎週月曜 10:00 週次報告` と打つと KV に保存され、
  実際にその時刻に自分宛 DM が届き、翌週も再発火する。
  確認方法: mm.w4ta.com にデプロイし、直近数分後の時刻で繰り返しを登録して2回発火を目視確認。
  RHS はまだ無くてよい(スラッシュコマンドのみ)。

  - [x] **T1: データモデルと KV 層** — `Reminder` 型(id / userID / message / schedule / nextRunAt /
        createdAt)と、ユーザー単位の一覧・取得・保存・削除を `server/store/kvstore` に実装する。
        完了条件: Go のユニットテストで CRUD が通る。
  - [x] **T2: 次回発火時刻の計算** — 繰り返し表現(毎日 / 平日 / 曜日指定 / 毎月N日 + 時刻)の内部型を定義し、
        「ある時刻の次の発火時刻」をユーザー TZ で計算する関数を書く。
        完了条件: TZ・月末・曜日跨ぎを含むテーブルテストが通る。
  - [x] **T3: スケジューラ配線** — `OnActivate` で `cluster.JobOnceScheduler` を起動し、
        発火コールバックで DM を送ってから T2 で次回を計算して `ScheduleOnce` を再予約する。
        起動時に KV から既存リマインダーを復元する。
        完了条件: ローカルで1分後の繰り返しを登録し、2回発火する。
  - [x] **T4: スラッシュコマンド** — `/recurring` を登録し、`毎週月曜 10:00 <本文>` 相当の
        最小パースと `list` / `delete <id>` サブコマンドを実装する。
        完了条件: パーサーのユニットテストが通り、コマンドの応答が返る。
  - [x] **T4b: レビュー指摘の修正** — スケジューラの再設計、DST 遷移日の日スキップ、
        配信中に削除されたリマインダーの復活、tzdata の埋め込み、1ユーザーあたりの件数上限、
        配信失敗の打ち切り、無効化ユーザーのデータ削除、ルーン/バイト長の混同、
        `strings.ToLower` のオフセット問題を修正し、配信スイープの統合テストを追加した。
  - [x] **T5: 自サーバーで実証**(2026-09-03 完了) — mm.w4ta.com にインストールし、
        `/recurring daily 22:10 発火テスト` を登録。22:10 に DM が届き、
        本文に `next Fri, 4 Sep 22:10 JST` が入って次回が翌日へ進むことを確認した。
        配信スイープは `NextRunAt` を過ぎたものを拾う方式なので、
        次回時刻が正しく前進していれば以後も鳴る。

        導入時に判明したこと:
        - この docker compose は `environment` に列挙した変数だけをコンテナに渡すため、

          ルートに引数とサブコマンドを両方持たせていたため。実機に入れるまで気づけなかった

## 実機でしか見つからなかった不具合(2026-09-03)

ユニットテストと CI が全部通っている状態で、実サーバーに入れて初めて分かったものが3件。
いずれも「Mattermost 本体が値をどう使うか」の取り決めに関するもので、
プラグイン単体のテストでは踏めない層にある。

1. **オートコンプリートのルートに引数とサブコマンドを両方持たせていた** →
   コマンド登録が失敗し、OnActivate ごと落ちてプラグインが起動しなかった。
   `registerCommand` を一度もテストで呼んでいなかったため気づけなかった。
2. **ボタンの Action ID に空白が入っていた** → コールバックが 404。
   Mattermost はこの ID を自身の経路 `/api/v4/posts/<id>/actions/<action id>` に
   そのまま入れる。
3. **同じ ID の下線も 404、かつ integration URL がプラグインパスを含んでいなかった** →
   `unsupported protocol scheme ""`。下線は URL エスケープで変化しないため、
   2 の修正時のテストでは捕まえられなかった。URL は
   `/plugins/<plugin id>/...` から始まる完全なパスが必要。

現在は `IsValid()` の呼び出し、Action ID の英数字チェック、
URL のプレフィックス検証をテストに入れてあるが、
**この層は実機確認を省略できない**。M2 の RHS は webapp が絡むぶん
さらにその傾向が強くなるので、小さく作って都度実機で確認する。

## レビューで判明した要検討事項(2026-09-03)

- **チャンネル宛リマインダーを M2 に上げるべきか**。「やらないこと」に置いたが、
  レビューでは「インストールを決めるのは管理者で、彼らが見るのはチームに効くかどうか。
  DM 限定ではサーバー全体に入れる動機が薄い」との指摘。Slack の `/remind #channel` 相当が
  最も使われている用途でもある。**未決**。
- ~~**発火した DM に操作導線がない**~~ → 2026-09-03 実装。配信メッセージに
  「Snooze 15 min」「Snooze 1 hour」「Stop this reminder」のボタンを付けた。
  押すと投稿がその結果に書き換わり、ボタンは消える。
  スヌーズは発火した回だけを後ろにずらし、スケジュール自体は変えない。
- `delete` の引数を `AddDynamicListArgument` にすれば、16文字の ID をコピペする必要が消える。
  `server/api.go` にルータは既にある。RHS を待たずに実装できる。
